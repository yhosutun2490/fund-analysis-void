# 部署到 Cloudflare 與環境變數管理

本專案用 Void（`void@1.2.1`）建置，部署到**自己的 Cloudflare 帳號**（Void 文件稱為「direct Cloudflare target」）。
部署後會有：一個 Worker（API + Swagger UI）、一個 D1 資料庫、每日 cron，以及寄驗證碼信用的 Email Sending。

> 本文的內容依據本機 `node_modules/void/docs` 與 Void 原始碼整理（2026-10-25），**還沒有實際部署驗證過**。
> 第一次部署後，請把實際遇到的狀況補回來。

---

## 1. 部署會做哪些事

`void deploy` 一次跑完下面這些（見 `node_modules/void/docs/integrations/cloudflare.md` 的「What happens during deploy」）：

```
void deploy --platform cloudflare
  ├─ 建立缺少的資源（D1…），把資源 ID 寫進 void.lock.json
  ├─ 建置（vite build → dist/ssr）
  ├─ 檢查 schema 漂移：db/schema.ts 有改動但沒產生 migration → 直接停止
  ├─ 先存一個 D1 Time Travel 還原點，再套用 db/migrations/ 的 migration（含 Better Auth 的資料表）
  ├─ 缺少 BETTER_AUTH_SECRET 時自動產生
  ├─ 設定 Email（第一次會列出網域 / DNS 變更，問你要不要套用）
  ├─ 上傳 Worker → 驗證新版本可以正常回應 → 才切換流量
  └─ 更新 cron trigger（crons/daily-ingest.ts：每天 UTC 23:00）
```

## 2. 第一次部署前的檢查清單

| # | 項目 | 位置 | 狀態 |
|---|---|---|---|
| 1 | 寄件地址必須在自己帳號內的 zone | `src/lib/email.ts` 的 `EMAIL_FROM` | ❌ 目前是佔位值 `REPLACE-WITH-YOUR-MAIL-DOMAIN.example` |
| 2 | D1 `database_id` | `void.config.ts` | ⚠️ 佔位值，可以讓 Void 自動建立（見下方說明） |
| 3 | schema 有改就先產生 migration | `npm run db:generate` | 部署會檢查漂移 |
| 4 | Lipper 資料授權 | `/api/*` 目前不用登入、開放 CORS | ⚠️ 部署到公開網址前要先決定怎麼保護 |

### 寄件網域（第 1 項）

- 寄件網域必須是 Cloudflare 帳號內自己的網域。建議用子網域，例如 `noreply@mail.your-domain.com`，這樣原本網域的 MX 記錄不會被動到（Void 拒絕覆蓋其他服務商的 MX）。
- **Workers Free 方案只能寄給驗證過的收件人**：要先把收件信箱加到 Cloudflare 的 **Email Routing → Destination addresses**，並完成驗證。驗證碼只會寄給管理員自己，所以把 `ADMIN_EMAILS` 裡的每個信箱都驗證過就夠用。
- 要寄給任意收件人，就需要 Workers Paid 方案，並完成 Email Sending onboarding。

### D1 的 `database_id`（第 2 項）

查過原始碼（`provision-*.mjs` 的 `isRealD1Id`）：`database_id` 不是 UUID 格式時，Void 會視為「尚未建立」，部署時就用 `database_name`（`fund_risks`）**建立新的資料庫，或沿用同名的既有資料庫**，再把 ID 存進 `void.lock.json`。

所以有兩種做法，選一種就好：

- **A. 交給 Void**：保留佔位值直接部署，部署完把 `void.lock.json` commit 進版本控制。
- **B. 自己建立**：先跑 `npx wrangler d1 create fund_risks`，把回傳的 ID 填進 `void.config.ts`（README 寫的就是這個做法）。

> 第一次部署請只在**一台機器**上跑，跑完立刻 commit `void.lock.json`，否則可能重複建立資源。

## 3. 部署步驟

```bash
# 0. 確認建置、型別、測試都通過
npm run typecheck && npm test && npm run build

# 1. 記住部署目標（只要做一次；.void/ 不進版本控制，換台機器要重做）
npx void connect --platform cloudflare     # 開瀏覽器登入、選帳號

# 2. 部署
npm run deploy                             # = void deploy
#   還沒跑過 connect 的話：npx void deploy --platform cloudflare

# 3. 設定 secret（Worker 要先存在，所以放在第一次部署之後）
npx wrangler secret put ADMIN_EMAILS --name fund-risks-analysis
npx wrangler secret put DISCORD_WEBHOOK_URL --name fund-risks-analysis   # 選用

# 4. commit 部署產生或更新的檔案
git add void.lock.json void.config.ts && git commit -m "chore: record Cloudflare resources"
```

### 部署後驗證

1. 打開 `https://fund-risks-analysis.<你的子網域>.workers.dev/`，應該會看到 Swagger UI。
2. 用 `ADMIN_EMAILS` 裡的信箱註冊、登入 → 呼叫 `POST /admin/ingest/challenge` → 確認收得到驗證碼信。
3. 帶驗證碼呼叫 `POST /admin/ingest` 手動抓一次資料，再用 `GET /api/meta/runs` 確認有寫入紀錄。
4. 到了 cron 時間（台灣時間早上 7:00）再看一次 `/api/meta/runs`。

### 日常操作

```bash
npx void project status       # 目前的部署狀態
npx void project logs         # 即時 log（Cloudflare 上是 live tail，不會保留歷史）
npx void project rollback     # 回到上一版程式碼（不會還原 DB migration）
npx void db restore ...       # 用部署時印出的還原點還原 D1（Free 方案保留 7 天，Paid 方案 30 天）
npx void secret list          # 列出線上 secret 的名稱（不會顯示值）
```

> rollback 只會還原程式碼。如果新版本加了 migration，rollback 之前要先確認舊版程式碼能不能跑在新的 schema 上。

## 4. 環境變數管理

### 三種存放位置

| 種類 | 放在哪 | 進版本控制？ | 適合放什麼 |
|---|---|---|---|
| **vars**（明文） | `void.config.ts` → `cloudflare.vars` | ✅ 會 | 非機密的設定，例如 `ANUE_PAGE_SIZE` |
| **secrets**（加密） | `wrangler secret put`，存在 Cloudflare | ❌ 不會 | 機密，或不想寫進 repo 的值 |
| **本機 `.env`** | 專案根目錄 `.env`（已列在 `.gitignore`） | ❌ 不會 | 本機開發用的值；**部署時不會上傳** |

- 程式統一從 `env`（Worker binding）讀取，型別定義在 `src/bindings.ts` 的 `Env` interface。
- Void 本機只讀根目錄的一份 `.env`。`.dev.vars`、`.env.local` 這類 Wrangler 或 dotenv 慣用的檔名都**不支援**。
- 每個變數只選一種存放方式。vars 和 secret 在 Worker 上都是 binding，名稱重複時 Cloudflare 會拒絕（尚未實測）。

### 本專案的變數清單

| 名稱 | 種類 | 必填 | 說明 |
|---|---|---|---|
| `DB` | D1 binding | ✅ | 在 `void.config.ts` 宣告，Void 負責建立 |
| `ANUE_PAGE_SIZE` | var | — | 已寫在 `void.config.ts`，值為 `"2000"` |
| `ADMIN_EMAILS` | secret | ✅ | 管理員 email 允許清單（逗號分隔）。沒設定就沒有任何管理員 |
| `DISCORD_WEBHOOK_URL` | secret | 選用 | 抓取失敗或帶警告時發 Discord 通知。沒設定就不通知 |
| `CHALLENGE_TTL_SECONDS` | var | 選用 | 驗證碼有效秒數，預設 600 |
| `CHALLENGE_RESEND_SECONDS` | var | 選用 | 重新要求驗證碼的最短間隔，預設 60 |
| `CHALLENGE_MAX_ATTEMPTS` | var | 選用 | 驗證碼最多可以錯幾次，預設 5 |
| `CHALLENGE_COOLDOWN_SECONDS` | var | 選用 | 手動觸發後的冷卻秒數，預設 600 |
| `BETTER_AUTH_SECRET` | secret | 自動 | Void 部署時自動產生，**不要手動設定** |

`CHALLENGE_*` 不是機密，要改預設值的話，加進 `void.config.ts` 的 `cloudflare.vars` 就好。

### ⚠️ 為什麼用 `wrangler secret put`，而不是 `void secret put`

Void 文件推薦用 `void secret put`，但它要求專案根目錄有 `env.ts`（用 `defineEnv()` 宣告 schema），而且只接受 schema 裡宣告過的名稱。原始碼 `env-validation-*.mjs` 的檢查：

```
secret: env.ts is required before setting production values.
secret: ${name} is not declared in env.ts.
```

本專案**沒有 `env.ts`**，所以 `void secret put` 會直接失敗。目前的做法是用 Wrangler 直接寫成 Worker secret：

```bash
npx wrangler secret put ADMIN_EMAILS --name fund-risks-analysis
```

- 根目錄沒有 `wrangler.jsonc`，所以一定要用 `--name` 指定 Worker 名稱（就是 `void.config.ts` 裡的 `cloudflare.name`）。
- `wrangler login` 和 Void 的 Cloudflare 登入是**分開**的，第一次要各登入一次。

### 之後可以考慮：改用 `env.ts`

在根目錄加一份 `env.ts`，可以換來：

- `void secret put` / `void secret sync` 上傳之前會先驗證值。
- `void deploy` 會檢查必填的 secret 是不是都設定好了，**漏設 `ADMIN_EMAILS` 就不讓部署**。
- `void env check` 可以檢查本機 `.env`；`void env check --remote` 可以檢查線上 secret 的名稱。

代價：`env.ts` 裡宣告的伺服器端變數都**必須是 secret**，不能再放在 `cloudflare.vars`。改之前要先決定 `ANUE_PAGE_SIZE`、`CHALLENGE_*` 要搬成 secret，還是不放進 schema。

## 5. 其他注意事項

- **資料授權**：回傳的資料含 Lipper 授權指標（`lipperid`），只能內部使用。部署到公開的 `*.workers.dev` 網址，資料就等於公開了。可以考慮：
  - 在前面加一層 Cloudflare Access（Zero Trust）登入。
  - 或是讓 `/api/*` 也要登入才能讀。
  - 或是設定 `workers_dev: false`，只綁定受保護的自訂網域。
- **Workers Free 的限制**：Worker 壓縮後的大小上限是 3 MB（目前 `dist/ssr/index.js` 壓縮後約 231 KB）。CPU 時間和每日請求數也都有限制，每日 cron 要抓全站資料，要留意 CPU 用量。
- **不支援 Cloudflare 的 named environments**（`--env staging`）。要做 staging 的話，得另外準備一份 Void 專案設定。
- **auth 的速率限制**：部署後 Better Auth 預設依 IP 限制請求，例如 10 秒內最多嘗試登入 3 次，而且每個 Worker 實例各算各的。
