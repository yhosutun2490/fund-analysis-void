# 專案學習路線：由內而外的合約優先順序 (Drizzle + Zod ➔ Void)

## 核心問題
> **「學習路線可以先從 Void type-safe，再到 Drizzle + Zod 嗎？」**

**結論：強烈建議反過來——先學 Drizzle + Zod（資料合約核心），再看 Void 的 Type-safe（外層框架膠水）。**

---

## 為什麼不建議先學 Void Type-safe？

### 1. 現實落差：本專案未採用 Void 的路由與型別推導
- 在 `routes/_bridge.ts` 中，所有請求都被整包轉給 Hono：
  ```ts
  export const forward = defineHandler((c) => app.fetch(c.req.raw, c.env, c.executionCtx));
  ```
- Void 在此專案中僅負責打包建置與 Cloudflare Worker 綁定。
- 若先看 Void 的 `defineHandler.withValidator()` 或 `void/client`，在目前程式碼中找不到實際執行的範例，容易產生混淆。

### 2. 相依性倒置：Void 的 Type-safe 建立在 Drizzle-Zod 上
- Void 官方的 `void/drizzle-zod` 本質就是直接 re-export `drizzle-zod`。
- Void 的 request 驗證範例也是直接塞入 `createInsertSchema(table)`。
- 若不先理解 Drizzle 如何將資料表欄位轉換為 Zod Schema，直接看 Void 驗證只會流於語法糖，無法理解型別流動的底層機制。

### 3. 內功 vs 招式（通用性不同）
- **Drizzle + Zod（內功）**：無論未來架構是 Hono、Express、Next.js 還是 Fastify，「以 DB 作為單一真相來源、衍生 Zod Schema、以 `strictObject` 捕捉欄位漂移、在 Runtime 攔截不合約資料」的模式皆完全通用。
- **Void Type-safe（招式）**：僅是特定框架將 Zod 綁定至 request 參數與前端編譯期推導的語法封裝。

---

## 推薦學習路線：由內而外（Data Contract First）

```
Step 1: Drizzle Schema (資料來源真相)
  └── 理解 src/db/schema.ts (資料表定義、型別與 nullable 規則)
       ▼
Step 2: Drizzle + Zod 合約衍生與 Runtime 驗證 (專案核心靈魂)
  ├── 學習 createSelectSchema() 如何衍生欄位檢驗
  ├── 為什麼要用 z.strictObject() 而非 z.object()？(防止 API / DB 欄位漂移)
  ├── 理解 src/responses.ts 的 rowOf 模式與合約設計
  └── 理解 src/validation.ts 的 responds() 如何在資料送出前進行 runtime 攔截
       ▼
Step 3: 框架整合與 Type-safe (外層封裝與膠水)
  ├── 釐清「編譯期型別推導」與「Runtime 驗證」的差異 (見 note-learning/1)
  ├── 理解本專案 Hono 的 validate() 實作
  └── 了解若日後改為 Void 原生路由，如何使用 withValidator({ body, query, params })
```

---

## 學習驗證標準（對應 MISSION.md）

完成此學習路線後，應能達到以下目標：
1. **獨立說明原理**：能不看筆記解釋為什麼 `createSelectSchema + strictObject` 能防止 DB/API 欄位漂移。
2. **手寫 Response Schema**：能為一條全新回傳 DB 資料的路由，獨立寫出 `rowOf` 風格的 response schema。
3. **正確銜接驗證層**：能將寫好的 schema 透過 `responds()` 掛載至路由，在執行期驗證回應內容。
4. **透析框架差異**：能清楚指出 Void 內建功能做得到什麼（Request runtime 驗證 + Response 編譯期型別）、做不到什麼（Response runtime 驗證需自理）。
